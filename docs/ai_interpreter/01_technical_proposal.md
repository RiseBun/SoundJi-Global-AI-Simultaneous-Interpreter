# AI 同声传译助手技术提案

版本：v0.2

项目定位：Term-aware Interpretation & Review Workspace，术语可控的 AI 同传学习助手。

本文档属于技术提案，回答的是：这个变化该不该做，为什么现在做，解决什么问题，影响范围多大，有哪些替代方案，为什么选择当前方向。具体系统组件、API、状态机和表结构不在本文展开，分别进入架构设计和实现设计。

三类文档边界如下：

| 文档 | 决策层级 | 回答问题 | 本项目产出边界 |
|---|---|---|---|
| 技术提案 | 高层决策/共识层 | Why / Whether：这个变化该不该做 | 论证动机、目标用户、痛点证据、竞品边界、替代方案、是否进入 MVP。 |
| 架构设计 | 系统结构/架构层 | System How：系统整体怎么组织 | 定义组件、职责边界、数据流、控制流、部署形态、治理要求。 |
| 实现设计 | 模块落地/实现层 | Module How：模块具体怎么落地 | 当前先定义对象、事件、状态机、异常和验收样例；不提前绑定 API endpoint 和表结构。 |

## 1. 提案摘要

一句话定位：面向英文技术分享和网课场景的 AI 同声传译助手，把“会前术语控制、会中稳定字幕、会后双语复盘”做成可验证闭环。

建议立项一个面向跨语言学习、网课、技术分享和轻量会议场景的 AI 同声传译助手。它不是通用实时翻译窗口，而是一个围绕“准备 - 实时 - 复盘”的工作台：

- 会前导入课程主题、术语表和上下文材料。
- 会中提供双语字幕，并区分 partial 临时识别和 final 稳定字幕。
- 会中标记术语命中，让技术术语、专名、缩写的译法可控、可检查。
- 会中提供系统知识树：准备阶段先给出完整大标题骨架，播放过程中只补充当前相关小标题，让学习者在全屏观看时保留课程结构感。
- 会后沉淀双语时间轴、术语命中和 Markdown/JSON 导出材料。
- 可解释自动回修只作为 P2 差异化 demo 或待验证假设，不作为 MVP 主链路承诺。

核心判断：主流会议和字幕产品已经覆盖“实时字幕、翻译字幕、会后 transcript/summary”的部分能力，但对技术学习者需要的“术语可控、字幕状态稳定、会后可复盘”的闭环支持不足。普通实时翻译字幕主要展示当下译文，本方案强调会前术语约束、会中 partial/final 状态和会后双语证据链，因此值得进入 MVP。

## 2. 背景与问题

实时字幕和翻译能力已经变成 Zoom、Teams、Google Meet、腾讯会议、飞书妙记、通义听悟等产品的常见能力。官方竞品扫描和用户痛点采样显示，市场不缺“显示字幕”的功能，缺的是更适合学习和技术内容的解释型工作流。

本项目前序调研把问题拆成六类：

| 痛点 | 当前证据强度 | 结论 |
|---|---:|---|
| 术语/专名错译 | 中 | 跨语言、跨产品有初步信号，官方热词/术语功能也侧面确认其重要性。 |
| 字幕延迟/跟不上节奏 | 中低 | 是实时字幕评价维度，但公开用户痛点证据不够强。 |
| 字幕跳动/不稳定 | 中低 | 需要拆成文本反复变化和视觉闪烁两类，不能混写。 |
| 前文错误无法自动回修 | 低但有价值 | 更适合作为差异化能力缺口，而不是已充分验证的普遍痛点。 |
| 会后不可追溯/难复盘 | 中高 | 用户关心 captions 是否随录制保存、transcript 是否可下载/恢复、多语言 transcript 是否覆盖。 |
| 网课/技术分享不适配 | 中 | DeepLearning.AI/Coursera 社区样本直接指向字幕时间轴和字幕偏慢；HN/V2EX 支持技术内容和学习工作流信号；B 站搜索线索和官方产品页只作低权重线索/反证。 |

因此，本提案不把“翻译准确率最高”作为唯一目标，而把目标改成：让学习者能够在实时场景中获得足够可用的翻译，并在会后追溯、修正和复盘。

### 2.1 知识树机会

对技术学习者来说，字幕只能解决“听懂这一句”，不能自动解决“这一句在课程体系中的位置”。英文技术分享、网课和会议往往存在连续概念铺垫：先讲目标和边界，再讲 API、向量库、延迟、术语和导出。如果用户只盯着字幕，容易漏掉大结构。

因此，系统知识树是本项目的关键差异化方向：

- 准备阶段：先展示完整大标题骨架，让用户知道课程会按哪些主题展开。
- 播放阶段：随着 final 字幕推进，只在对应大标题下补充当前小标题，保持结构增长感。
- 全屏观看阶段：利用视频左右黑框显示白字浮动树，减少对视频主体内容的遮挡。
- 复盘阶段：知识树和双语时间轴一起导出，帮助用户按结构回看。

当前文档中的知识树不是无引用总结，也不是完整知识图谱。MVP 先用 mock contract 和可视 demo 证明展示方式，真实 LLM 生成、跨课程知识图谱和长期学习画像都不进入 P0。

## 3. 目标用户

| 用户层 | 场景 | 主要痛点 |
|---|---|---|
| 留学生/跨语言学习者 | 听英文网课、公开课、技术讲座 | 专业词、专名、缩写容易错；字幕跟不上讲解；会后难复盘。 |
| 技术从业者 | 观看英文技术分享、发布会、论文讲解 | 代码、API 名、模型名、论文术语错译影响理解。 |
| 跨国团队成员 | 参加培训、评审、例会 | 实时理解和会后追溯都重要，但会议工具更偏会议纪要。 |
| 听障或非母语用户 | 依赖字幕理解课程和会议 | 字幕准确性、同步性、可保存性直接影响可达性。 |

MVP 优先选择“个人学习者观看网课/技术分享”作为主场景，而不是多人会议主持、商业同传活动或大型直播平台。

## 4. 机会判断

### 4.1 竞品能力边界

调研中的官方/产品能力可归纳为四类：

- 会议工具：Zoom、Teams、Google Meet、腾讯会议等，强在会议入口、字幕和 transcript，但学习化复盘弱。
- 会议记录工具：Otter、飞书妙记、通义听悟等，强在会后文本和摘要，但会前术语约束和学习化双语复盘弱。
- 翻译工具：DeepL、Google Translate、有道同传等，强在翻译能力，但缺少会前术语约束和会后证据链。
- 字幕/浏览器工具：Live Caption、QQ 浏览器实时字幕、字幕插件等，强在轻量入口，但缺少结构化学习工作台。

这说明本项目不应和会议工具比全量会议管理，也不应和通用翻译工具比单句翻译，而应切入“面向学习者的术语约束、字幕状态稳定与学习化复盘”。

### 4.2 证据分级

前序采样使用以下来源等级：

- O1：官方确认/官方公告。
- U1：公开用户原话。
- U2：应用商店/产品评论。
- U3：官方社区/论坛用户帖。
- S1：二手文章/测评/媒体转述。
- S2：聚合榜单/营销文。
- I：工程推断。

全局可信度：

- A：官方文档/官方回复/官方公告。
- B：跨渠道重复用户证据或高质量官方论坛用户帖。
- C：单点公开用户原话或单条产品评论。
- D：二手转述或工程推断。

本提案的强论据只使用 A/B/C；D 级只作为线索，不作为核心结论。官方能力反证只能证明“已有产品覆盖到某个能力或场景”，不能替代用户痛点证据。

### 4.3 可写入方案的证据边界

| 结论类型 | 可以写 | 不能写 |
|---|---|---|
| 已较强验证的痛点 | 术语/专名错译、会后可追溯/可下载/可恢复、多语言 transcript 覆盖，是公开证据较集中的问题。 | 用户普遍明确要求双语时间轴和术语命中记录。 |
| 中等强度机会 | 网课/技术分享场景存在字幕时间轴、字幕偏慢、技术内容自动字幕质量和学习辅助工作流信号。 | 国内用户已被充分验证为强需求。 |
| 差异化假设 | 术语命中解释、P2 前文回修 demo、学习化复盘值得作为差异化方向验证。 | 实时自动回修已经是公开用户普遍痛点。 |
| 官方能力反证 | 腾讯会议、飞书妙记、QQ 浏览器实时字幕等说明会后沉淀或网课字幕已有产品覆盖。 | 竞品已经完整解决学习型双语复盘。 |

## 5. 方案选择

### 5.1 推荐方案

推荐建设“Term-aware Interpretation & Review Workspace”：

```text
准备阶段：课程主题 / 术语表 / 上下文材料
  -> 实时阶段：ASR partial/final 字幕 + 翻译 + 术语约束
  -> 复盘阶段：双语时间轴 + 术语命中 + Markdown/JSON 导出
  -> P2 可选：伪数据 Revision demo，用于解释差异化方向
```

### 5.2 方案对比

| 方案 | 优点 | 问题 | 结论 |
|---|---|---|---|
| 通用实时翻译窗口 | 最快做出 demo | 容易变成模型调用壳，差异化弱 | 不建议作为最终定位。 |
| 会议记录/纪要助手 | 会后价值明确 | 和 Otter、飞书妙记、通义听悟重叠 | 可借鉴，不作为核心。 |
| 字幕翻译插件 | 入口轻、易演示 | 数据和复盘链路弱 | 可作为 MVP 入口之一。 |
| 术语可控的 AI 同传学习助手 | 差异化清晰，可解释、可复盘 | 工程边界更多，需要控制 MVP | 推荐。 |
| 浮动系统知识树 | 能把字幕流组织成课程结构，适合技术学习者 | 真实生成质量和信息密度需要控制 | 作为 P1 差异化展示，P0 保留对象契约和 mock demo。 |

## 6. 范围

### 6.1 MVP 范围

MVP 只做一条主链路：

```text
输入固定英文技术分享音频或模拟流
  -> 按时间片生成 partial/final 原文字幕
  -> 生成中文翻译
  -> 根据术语表标记关键术语
  -> final 字幕进入双语时间轴
  -> 导出 Markdown/JSON 双语 transcript
```

### 6.2 明确不做

- 不做大型会议平台，不实现日程、参会人、会议室、权限组织。
- 不接入真实 Zoom、Teams、Google Meet 等会议平台。
- 不承诺专业会议级同传质量。
- 不做全语言覆盖，MVP 先做英文到中文。
- 不做实时人声合成配音，MVP 只做字幕和复盘。
- 不做完整实时自动回修；自动回修只作为 P2 伪数据/解释性 demo。
- 不做多说话人分离、PDF/SRT/VTT 全格式导出或云同步。
- 不承诺 P0 已经能真实自动生成完整知识树；P0/P1 只证明知识树对象、浮动展示和 mock 增量更新。
- 不采集隐私会话作为训练数据。

## 7. 成功指标

| 维度 | MVP 指标 |
|---|---|
| 可运行 | 固定样例输入 8-12 句技术内容，能按顺序播放并输出双语时间轴。 |
| 可控 | 至少加载 8 个术语，demo 中至少 5 个术语被命中并可见。 |
| 可稳定 | partial 不进入最终导出，final 固定进入时间轴且不被静默覆盖。 |
| 可复盘 | Markdown/JSON 导出包含时间、英文、中文、术语命中。 |
| 可结构化学习 | 知识树准备阶段展示大标题骨架，播放阶段能根据 final 字幕补充当前小标题；浮动视图不遮挡视频主体。 |
| 可验证 | 每条 final 都有中文译文和时间轴记录，支持人工对照验收。 |
| 可演示 | 3 分钟内展示术语导入、字幕播放、翻译、时间轴和导出完整闭环。 |

## 8. 风险与缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| 实时 ASR 延迟过高 | 影响同传体验 | MVP 允许准实时；用 chunk/partial/final 状态明确体验边界。 |
| 翻译错误被误信 | 学习误导 | 保留原文、术语命中、降级提示；P2 回修必须标注为 demo。 |
| 自动回修证据不足 | 价值叙事被质疑 | 写成差异化假设，不写成已验证普遍痛点。 |
| 中文用户证据不足 | 市场判断偏英文样本 | 文档中标注证据等级，中文侧继续补样。 |
| 竞品已有会后纪要 | 差异化变弱 | 聚焦双语时间轴、术语命中、技术学习复盘，而不是泛纪要。 |
| 隐私和合规 | 会议内容敏感 | 默认本地样例/用户主动上传；记录数据保留策略和删除机制。 |

## 9. 答辩口径

建议答辩开头使用：

1. 我们不是再做一个实时字幕壳，而是把技术场景最痛的术语准确、字幕稳定和会后复盘连成闭环。
2. 这个 MVP 的边界很清楚：固定技术分享输入，验证术语控制、partial/final 状态和双语时间轴导出。
3. 自动回修很有差异化，但证据和实现风险都高，所以我们把它放在 P2 demo，而不是 P0 承诺。

必须避免的夸大表达：

1. 已经证明所有用户都需要实时自动回修。
2. 本方案比 Zoom/Teams/Google Meet 翻译字幕全面更好。
3. 已支持真实会议平台、生产级低延迟和完整多语种同传。

## 10. 决策

建议接受本提案，进入架构设计与 MVP 实现阶段。

立项理由：

- 用户问题有足够信号，尤其是术语/专名、会后复盘、网课技术内容不适配。
- 主流产品能力边界清晰，仍有术语命中解释和学习复盘空间。
- MVP 可以做成可运行纵切，不依赖完整会议平台。
- 能体现 XEngineer 评分关注的产品判断、架构边界、Agent/Tool 能力、验证证据和交付路径。

## 11. 进入下一阶段的条件

进入架构设计前，需要统一以下决策：

- 产品主场景：个人学习者观看英文网课/技术分享。
- 首语种：英语到中文。
- 输入形态：MVP 先支持文件上传/模拟流，后续再支持浏览器音频捕获。
- 输出形态：双语时间轴、术语表命中、Markdown/JSON transcript；修订 diff 作为 P2。
- 工程策略：先 mock/real 可切换，再接真实 ASR/LLM。
